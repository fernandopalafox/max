## Representational Bottleneck Experiment

### Motivation

The previous LR sweep (May 8–9) showed that offline adaptation of the CartPole dynamics to a 5× pole environment plateaus around reward 524 (dense OGD) and 550 (LoRA-XS OGD at lr=1e-6). A natural question is: how much of this ceiling is due to data scarcity (50k transitions) versus the fundamental limitation of forcing Task B's physics through a latent space shaped by Task A?

To answer this, we run a structured three-point comparison:

1. **Skyline** — train a fresh TDMPC2 agent from scratch on CartPole 5× pole (Task B). This is the unconstrained upper bound: the latent space is perfectly shaped for the new task.

2. **Oracle** — load the frozen Task A encoder E_A and value function V_A from `baseline_new`, then train only the dynamics f_θ on a large (500k-step) Task B buffer using pure consistency loss (OGD trainer). This is the best possible adaptation under the frozen-representation constraint with sufficient data.

3. **Low Data** — same setup as Oracle but with only 50k transitions. Shows how much performance is lost to data scarcity alone.

The two gap metrics:
- **Skyline − Oracle** = cost of the frozen-encoder assumption (representational bottleneck)
- **Oracle − Low Data** = efficiency gap from data scarcity

All adaptation runs use all 4 `baseline_new` source models to average out variance from the choice of frozen encoder. The oracle buffer is collected once and shared across all 4 runs.

After the runs complete, the existing LR sweep plot (`logs/lr_sweep.png`) will be redrawn with horizontal lines at the mean Oracle and Skyline rewards.

### Setup

**Phase 2 — Skyline (Task B from scratch)**
- Config: `configs/pretrain_cartpole_5x_tdmpc2.json`
- Environment: CartPole balance, `cartpole_pole_length_scale: 5.0`
- Trainer: vanilla TDMPC2, 500k steps, 4 seeds (seeds 44–47)
- Save dir: `data/models/cartpole/skyline/run_{1..4}/`
- W&B project: `pretrain_cartpole_5x`

**Phase 3a — Collect oracle buffer (500k steps)**
- Config: `configs/collect_cartpole_oracle.json`
- Policy: π_A (baseline_new/run_1), `explore: true`
- Environment: CartPole balance, 5× pole
- Output: `data/collect/cartpole_oracle/<timestamp>/buffer.npz`
- W&B project: `collect_cartpole_oracle`

**Phase 3b — Oracle adaptation (4 runs)**
- Configs: `configs/finetune_cartpole_oracle_dense_ogd_run{1..4}.json`
- Each run: dense dynamics warm-started from `baseline_new/run_N/final.pkl`
- Trainer: `ogd` (consistency-only MSE loss; frozen encoder, critic, policy, reward)
- lr=0.0003, 200k SGD steps, eval every 10k steps in 5× pole env
- W&B project: `finetune_cartpole`, run names: `dense_ogd_oracle_run{1..4}`

**Phase 4a — Collect low-data buffer (50k steps)**
- Config: `configs/collect_cartpole_lowdata.json`
- Same policy and environment as oracle collection, independent draw
- Output: `data/collect/cartpole_lowdata/<timestamp>/buffer.npz`

**Phase 4b — Low-data adaptation (4 runs)**
- Configs: `configs/finetune_cartpole_lowdata_dense_ogd_run{1..4}.json`
- Same structure as oracle configs but with 50k buffer and 100k SGD steps
- lr=0.0003

## Equal-Compute Re-run (300k SGD steps each)

The initial runs used different step counts (oracle 200k, lowdata 100k), making compute a confound. Re-running both conditions at 300k steps to isolate the effect of data quantity from training compute. At 300k steps × batch 256: oracle sees each of its 500k transitions ~154 times; lowdata sees each of its 50k transitions ~1536 times. Groups `oracle_300k` and `lowdata_300k` in W&B project `finetune_cartpole`. Eval every 50k steps.

### Results (initial run — unequal compute)

All 12 runs completed overnight (single RTX 4090, sequential).

| Condition | run1 | run2 | run3 | run4 | mean |
|---|---|---|---|---|---|
| Skyline (scratch on Task B) | 992.2 | 977.9 | 965.9 | 960.1 | **974.0** |
| Oracle (500k buffer, frozen E_A) | 505.9 | 505.8 | 487.1 | 507.2 | **501.5** |
| Low Data (50k buffer, frozen E_A) | 668.1 | 614.6 | 434.4 | 518.3 | **558.9** |

**Gap metrics:**
- **Skyline − Oracle = 472.5** — large representational bottleneck. Freezing E_A costs ~48% of the achievable reward. Task A's latent space is a meaningful constraint for the 5× pole task.
- **Oracle − Low Data = −57.4** — the oracle is *worse* than low data despite 10× more transitions. More data at lr=3e-4 hurt rather than helped. Likely causes: (1) with 500k transitions the model sees each sample far fewer times before convergence, reducing effective training signal; (2) the more diverse oracle buffer contains harder-to-fit trajectories that increase gradient noise at this LR. The low-data regime may benefit from implicit regularization (repeated exposure to the same samples).

Skyline rewards are from the wandb API (`clearoboticslab/pretrain_cartpole_5x`). Oracle and lowdata rewards are final-step eval from the finetune script output.

# Phase 2 — Skyline
for seed in 44 45; do gpu=$((seed-44)); \
  conda run -n max python scripts/train.py \
    --config pretrain_cartpole_5x_tdmpc2.json \
    --gpu $gpu --seed $seed \
    --save-dir ./data/models/cartpole/skyline/run_$((seed-43)) \
    --run-name skyline_$((seed-43)) & \
done; wait
for seed in 46 47; do gpu=$((seed-46)); \
  conda run -n max python scripts/train.py \
    --config pretrain_cartpole_5x_tdmpc2.json \
    --gpu $gpu --seed $seed \
    --save-dir ./data/models/cartpole/skyline/run_$((seed-43)) \
    --run-name skyline_$((seed-43)) & \

conda run -n max python scripts/collect.py --config collect_cartpole_lowdata.json
